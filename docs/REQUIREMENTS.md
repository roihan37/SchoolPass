# SchoolPass Requirements

## Core flow
1. Parent and Teacher register with name, email, password, and role; registration does not require a class code.
2. A Teacher creates multiple classes and shares a generated join code for each class.
3. A Parent joins a class with its code and a child name. The server links that child to the authenticated Parent; the Parent can join multiple classes.
4. Parent retrieves only their own children and creates a leave request for one `absenceDate`, with `type` SICK or PERMISSION and nonempty `reason`. Initial status is PENDING.
5. Teacher can list/review only requests for their assigned classes.
6. Teacher decides APPROVED or REJECTED. For REJECTED, `decisionReason` is required. Decision is final in this MVP.
7. Parent sees the status from the database.
8. Optional P1: parent uploads one private supporting file while request is pending; teacher/parent access only after server authorization; approved/rejected decision causes in-app notification; dashboard summary uses cache.

## Business rules
- BR01: Parent must own the target Student. No `parentId` from client can override authenticated identity.
- BR02: A Student can have at most one leave request per calendar date: database UNIQUE(studentId, absenceDate).
- BR03: Only assigned Teacher can read or decide a class's requests.
- BR04: Only PENDING can transition to APPROVED or REJECTED. Use a conditional DB write for concurrent decisions.
- BR05: Rejection requires a reason; approval reason optional.
- BR06: Private attachments are accessible only to owning parent and class teacher. Do not expose public MinIO buckets.
- BR07: Notification processing may retry; unique DB constraint prevents duplicates.
- BR08: Use fictional seed records; no real sensitive student data.
- BR09: Parent and Teacher registration validates role and unique email; passwords are hashed before storage.
- BR10: Only Teacher can create classes; class names are unique per Teacher. Join codes are generated by the server and stored as hashes.
- BR11: Only Parent can enroll a child. Parent identity comes from the authenticated server identity, never a client-supplied parent ID. Each Student belongs to one Parent and one class; a Parent can have students in multiple classes.

## Nonfunctional requirements
- TypeScript strict; meaningful validation and HTTP statuses.
- Modular architecture, clear error paths, no secret leakage.
- Responsive UI with reusable components, loading/error/empty states.
- Repeatable build/test and Docker-based local services.

## Acceptance scenarios
- Parent can authenticate and see only own students.
- Parent can create a request, then list and inspect it.
- Second request for same student/date is rejected with HTTP 409.
- Another parent cannot create/read a request for unrelated student (403 or 404 per API policy, consistently applied).
- Teacher for unrelated class cannot approve or read a student's request.
- Two simultaneous decisions cannot both succeed.
- Retry of a notification job does not duplicate its DB record.
- A newly registered Teacher can create two classes; a registered Parent can enroll a child into both, and sees only those classes and children.
- A second Parent enrolling into the same class creates a child associated only with that second Parent; a Teacher cannot use the Parent enrollment endpoint.
